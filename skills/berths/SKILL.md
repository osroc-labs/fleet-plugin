# Berths: a simulator or emulator on demand

A berth is a simulator (or Android emulator) slot on a Mac in the user's Fleet. Everything goes through the fleet MCP.

1. **See what's free:** `fleet_status`. Berths that are `ashore` are free; `adrift` means that Mac is offline.
2. **Open a voyage:** `voyage_start` with a one-line `goal` and `repo` from `git remote get-url origin` (leave it out outside a repo). The voyage is the run: its leases and every op go in its log, and `voyage_close` at the end releases anything still held. Reuse the one you opened earlier in this conversation instead of opening another.
3. **Lease:** `lease` with `voyage_id` and `target` `iphone`, `ipad` or `appletv`. Plain `iphone` is the default iPhone (the newest Pro); pick another model by name where a Mac has it: `iphone:pro max` (largest), `iphone:17e` (smallest, a notch), `iphone:air`. To test on the iOS your users run, pass `runtime`: `newest` (the highest release in the fleet), `previous` (the newest release of the major before), `beta`, or a version like `26.6`; the result's `runtime` says which you got, a Mac that has it makes a berth on it if none is free, and when no Mac has it the lease fails saying how to install it (don't fall back to another version without saying so). Other iPhone models exist on a Mac only when its owner added them on the Mac's page; with none free the lease fails and says so. Leasing again on the same voyage gives the same berth back (or a berth on another Mac when its Mac went offline). A lease expires after `ttl_seconds` (default 1800) without ops; each op, and leasing again, extends it. `sticky: true` gives the project its own berth that keeps apps and sign-ins between leases; erase it with `release` `reset` (or `reset_berth` when no lease holds it), and `unpin` gives it back to the fleet.
4. **Boot** if it isn't: `boot`. The first boot of a berth can take about 40 seconds.
5. **Put the app on it:**
   - **The project's builds first.** When the project's builds are in Fleet (the EAS webhook from the project page's Builds tab, `fleet builds sync` in the repo, or `register_build` right after your own `eas build`), install with `install_app { profile: "preview-simulator" }`: Fleet picks the newest build of that EAS profile for the berth's platform (an iOS simulator build or an APK) and says which one (build id, fingerprint, channel, age). `builds { project }` lists them; `build_id` installs one exactly. `bundle_id` reinstalls the Mac's own cached copy, and on an up-to-date runner with none, the project's newest build of that id (it says so); to pick a particular build, use `profile` or `build_id`. If `profile` finds nothing it names the profiles that exist: pick one, or register the build first.
   - A build Fleet doesn't know: zip the `.app`, get `upload_url`, PUT the zip there, then `install_app` with `blob_key` (the `blobKey` that `upload_url` returned) and `launch_app` with the bundle id. An EAS **simulator** build goes in directly: `install_app` with `url` (`eas build:view <id> --json` → `artifacts.buildUrl`, from a profile with `"ios": { "simulator": true }`).
   - **Only simulator builds run on a berth.** A store or ad hoc `.ipa` (EAS's `production` or `preview` profile) is a device build, and `install_app` refuses it. No EAS simulator build? Build one here: in an Expo project, `fleet build-sim --profile preview --lease <lease id>` (prebuilds when there's no `ios/`, builds Release for the simulator, ad hoc signed so sign-in works, zips, uploads and installs). By hand: `npx expo prebuild -p ios`, `xcodebuild -workspace ios/<Name>.xcworkspace -scheme <Name> -configuration Release -sdk iphonesimulator -destination 'generic/platform=iOS Simulator' -derivedDataPath <scratch>/dd CODE_SIGN_IDENTITY=- CODE_SIGNING_REQUIRED=NO build`, `ditto -c -k --keepParent <scratch>/dd/Build/Products/Release-iphonesimulator/<Name>.app app.zip`, then `fleet install <lease id> app.zip` (or `upload_url` + `install_app` `blob_key`).
   - **Did it launch, and on which update?** On runner 0.8.0+ `launch_app` watches the app for a few seconds (`watch_seconds`, default 5) and says whether it **crashed** (exception, the crashed thread's frames, a link to the `.ips`) and, for an expo-updates app, which update is running (id, group, created, channel) and any newer one waiting for the next launch. To check a published update: `launch_app` with `wait_for_update_seconds`, and confirm the relaunch runs the update id you published. `app_logs` shows every crash report since the lease began.
   - **Over-the-air updates need the channel.** A local build gets a channel's EAS Updates only with the `expo-channel-name` request header in `ios/<Name>/Supporting/Expo.plist` (`EXUpdatesRequestHeaders`). `fleet build-sim --profile preview` sets it from `eas.json` for that build (and takes the profile's `EXPO_PUBLIC_*` env); `--channel <name>` sets it directly.
   - An Expo or Metro dev server, or any web page: `open_url` with the URL (`exp://…` or `https://…`). The berth can't reach `localhost` on this machine: if the `fleet` CLI is installed, `fleet expose <port>` gives a public URL to open instead. Or `lease` with `metro: <port>` (and `scheme`): the result is the `fleet expose` command to run in your shell, which tunnels the port for the lease's lifetime and opens the dev client on the berth (needs `cloudflared` and the `fleet` CLI).
6. **Look, then act:** `screenshot` and actually look at it. `describe_ui` gives the elements and their ids; `tap` by id, `type_text`, `swipe`, `press_button`. Screenshot again after each step that changes the screen.
7. **Did the update land? Replicas.** A project's replicas are berths kept on one installed runtime each (the simulator twin of a TestFlight or Play build) and the EAS Update channel that build listens to; `replicas { project }` lists them. After `eas update`, call `replica_check { project, expect_group: "<the group eas update printed>" }`: it launches each replica, waits for the download, relaunches and reads which group runs (past 45 s it says Still running: call `op_result` with its op_id). Report every row with its sentence: OK; BEHIND (another group or the embedded bundle runs, usually a fingerprint mismatch: the note gives the `eas fingerprint:compare` line); MISMATCH (the build listens to another channel); CRASHED; ERROR. A BEHIND or MISMATCH means the update didn't reach that runtime: say so, don't retry. Never lease or reset a replica's berth yourself. In a script: `fleet replicas check <owner/repo> --expect-from eas-update.json` (the saved `eas update --json`) exits 0 when all are ok, 3 when one isn't, 1 on an error.
8. **Maestro flows:** `run_flow` with the flow (or a zip of the flows folder). Credentials go by **name** only: `secrets: ["STAGING_SMOKE_EMAIL", "STAGING_SMOKE_PASSWORD"]` are filled in as `${NAME}` on the runner Mac and never come back to you. Never read a password into the conversation to pass as `env`. A missing name fails with the command the owner runs once on that Mac: `fleet secrets set <owner/repo> <NAME>` (or `fleet secrets import <owner/repo> <path to the project's .env> <NAME>...`). The other way: lease `sticky`, sign in once by hand, and run flows that skip sign-in. The app must be installed first; `app_id` becomes `${APP_ID}`, and a flow with no config section gets `appId: ${APP_ID}`. A flow given as text runs from the zip's root (or `flow_path`'s folder), so its `runFlow` paths resolve. `env` values become `${NAME}` and stay out of the log. Maestro stops at `timeout_seconds` (default 600, max 1800) and reports status `timeout`. A Mac needs Maestro and Java; the error says how to install them.
9. **Release and close:** `release` when you're done, every time, even after a failure, then `voyage_close` the voyage with a one-line `summary` of what you saw.

**Android berths** (Macs whose owner added them; runner 0.9.0+): `target` `android` (a Pixel 9, 1080×2424), `android:small` (1080×1920: Play's screenshot size) or `androidtablet` (Pixel Tablet), Android 16 (API 36) with Google Play and 16 KB pages. The same tools, with these differences:
- `install_app`: an `.apk` (`url`, or `upload_url` with `ext: "apk"` then `blob_key`); an `.aab` can't install, so build an APK (an EAS profile with `"android": { "buildType": "apk" }`, or `./gradlew assembleDebug`). `bundle_id` is the package name everywhere (`launch_app`, `app_logs`, reinstall from the Mac's cache).
- `tap`/`swipe` coordinates and `describe_ui` frames are **pixels**. `press_button`: `back`, `home`, `recents`, `lock`, `volume_up`, `volume_down`. `type_text` takes plain ASCII.
- `device_settings` adds `font_scale`, `animations`, `talkback`, `dont_keep_activities`, `orientation`, `network: "off"` (airplane mode) and `demo_mode` (12:00, full battery and signal: store-ready screenshots).
- `app_logs` is logcat for the package, with crashes from the crash buffer. `record_start` stops by itself at 3 minutes. No `push_notification`.
- `run_flow` runs Maestro flows on Android too. Metro works the same (`lease` `metro` and `scheme`, then the `fleet expose` command): the dev client opens the tunnel URL.

Rules:
- Always release the lease. A held berth blocks everyone else.
- Pass an `op_id` on every step (a stable name such as `login-tap-1`), so a retry never taps twice.
- Prefer `describe_ui` ids over coordinates.
- No call waits more than about 45 s. Slow steps answer within that: `run_flow` (Maestro flows take minutes), `boot`, `install_app`, `record_stop` and `launch_app` with `wait_for_update_seconds` say `Still running` with their `op_id` when they aren't done. Then call `op_result` with that `op_id` until the result comes. Don't start the step again: a retry with the same `op_id` returns the same result, passed or failed; use a new `op_id` to really run it again.

The user's quick look (one app or page, one screenshot, released) is `/fleet:sim`.
